1. O que é este projeto?

O WMK Remote Support já possui uma base real de acesso remoto. Seu código deriva do Airhand 0.2.3, um projeto em Rust com aplicativo desktop, Android, console web e servidor de retransmissão. Nosso objetivo é especializá-lo em assistência técnica a clientes, sem reescrever desnecessariamente o motor de vídeo e conexões.

Esta página é um inventário técnico, não uma certificação de qualidade. A indicação “já existe” significa que encontramos implementação e/ou documentação correspondente no código. Ainda são necessários testes em máquinas reais para confirmar a estabilidade desta versão WMK.

3. Como funciona internamente?

Computador do cliente (HOST)
captura tela + áudio e recebe mouse/teclado
↕ conexão autenticada e criptografada
Servidor relay próprio (QUIC / UDP 4433)
identifica e encaminha sessões quando necessário
↕ conexão autenticada e criptografada
Computador do técnico (CONTROLLER)
exibe a tela e envia comandos
Quando possível, um caminho direto substitui o relay para vídeo/áudio. O relay pode continuar transportando controle e metadados.

O mesmo programa desktop pode atuar como host (ser controlado) ou controlador (acessar outra máquina). O servidor faz o registro dos códigos e encaminha conexões. A comunicação direta depende da configuração de rede, NAT e firewall; ela não é garantida.

5. Primeiros passos para testar

  1. Preparar relay. É necessário um servidor acessível às duas máquinas, por exemplo uma VM Linux. O projeto fornece docker-compose.yml. O relay usa UDP 4433.
  2. Verificar certificado. Registrar e fixar o fingerprint SHA-256 do certificado do relay nos clientes. Não distribuir releases com certificado não configurado.
  3. Compilar. No Windows, usar o workflow GitHub Actions ou compilar com Rust, Node.js, CMake e MSVC. A configuração Tauri aponta para pacote NSIS.
  4. Instalar em máquinas autorizadas. Testar primeiro em dois computadores próprios antes de atender clientes.
  5. Conectar. Obter código de controle no host; informar no controlador; fazer o pareamento inicial e verificar que o host pode desconectar.
  6. Medir desempenho. Testar conexão LAN e internet, uso de CPU/RAM, latência, mudança de resolução, bloqueio de tela e reconexão.
git clone https://github.com/WalneyNF/WMK-Remote-Support.git
cd WMK-Remote-Support/client
npm ci
# Ajuste AIRHAND_SERVER e AIRHAND_SERVER_FP para seu relay confiável.
npm run tauri build
Importante: o workflow atual pode usar 127.0.0.1:4433 como endereço de teste. Um instalador gerado com isso não estará pronto para suporte via internet. Publicação para clientes exige relay público estável, fingerprint confiável e testes de segurança.

6. O que ainda não existe ou não está completo?

Transferir arquivos

Não implementado

Hoje há área de transferência de texto, não um gerenciador de arquivos remoto.

Chat e chamados

Planejado

Não há plataforma de ticket, atendimento, chat corporativo ou cadastro de empresas.

Diagnóstico técnico

Planejado

Painéis de saúde de disco, serviços, impressoras, rede e aplicativos ainda precisam de módulos próprios.

Assistente IA

Planejado

Não existe integração WMK com Groq/Ollama para análise de erros e orientação de suporte.

Idioma brasileiro completo

Parcial

README inicial em pt-BR; frontend mantém catálogos inglês/chinês e Rust possui idiomas internos próprios.

Identidade final

Parcial

Nome e ícone WMK em trechos da interface. Ícones binários do instalador, serviços e identificadores internos ainda usam referências legadas.

Outras limitações documentadas: microfone remoto exige condições específicas; acesso direto pode falhar em NAT simétrico; Android não pode iniciar compartilhamento oculto; console web termina a criptografia ponta a ponta no servidor onde é executado.

8. Ordem recomendada de evolução

  1. P0 — Estabilização: conseguir build Windows verde, executar em duas máquinas, certificar o pareamento, testar UAC e reconexão.
  2. P0 — Segurança: revisar autorização, permissões, logs, armazenamento de segredos, acesso não assistido e funcionamento do serviço SYSTEM.
  3. P1 — Localização: traduzir React, Rust, instalador, menus e Android para pt-BR sem quebrar mensagens de protocolo.
  4. P1 — Identidade: atualizar ICO/PNG/ICNS, nome do executável, nome do serviço e estratégia de migração de configurações.
  5. P2 — Atendimento: modo suporte rápido, chat, envio de arquivos autorizado, cadastro de cliente e histórico.
  6. P3 — Produtividade: diagnóstico de máquinas, relatórios, permissões por técnico, assistente IA opcional e integrações fiscais.

Veja o planejamento técnico em ROADMAP.md. Este documento descreve o estado atual; novas funcionalidades devem ser marcadas como concluídas somente depois de implementadas e testadas.
